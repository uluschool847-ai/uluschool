# Launch Compliance, Observability, and Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record verifiable enrolment consent, prevent personal data from leaking through email/Sentry, enforce the approved Render environment contract, and promote an isolated Frankfurt staging deployment to the public Kenya launch domain.

**Architecture:** Consent evidence is written with each new enquiry and surfaced to administrators while legacy records remain explicitly identifiable. Production-like startup is guarded by a pure environment validator. Shared redaction functions are connected to all Sentry runtimes. Deployment automation performs unauthenticated smoke checks, while the operator runbook owns secrets, staging isolation, role-based browser verification, Cloudflare DNS, and rollback decisions.

**Tech Stack:** Next.js 15 Metadata API and server actions, Prisma/PostgreSQL, Zod, Nodemailer, Sentry Next.js SDK, Vitest, Playwright, Render, Cloudflare DNS/R2.

## Global Constraints

- The public form never returns an internal `/admin/...` path or database ID.
- A new enquiry is rejected unless the server receives and validates `consentAccepted=true`.
- Consent time is generated by the server; the client cannot submit the stored timestamp or consent version.
- Existing enquiries remain readable with nullable consent fields and show `Legacy record - consent evidence not captured` in admin.
- Privacy copy identifies processors and operational practices but does not claim automatic ODPC registration or guaranteed legal compliance.
- User-controlled values are escaped before insertion into email HTML or headers.
- Environment validation reports variable names and invariant failures only, never values.
- Staging and Render production use `NODE_ENV=production`; `APP_ENV` distinguishes `staging` from `production`.
- Staging uses a separate database, separate private R2 bucket or prefix, separate Turnstile/Sentry configuration, and no production personal data.
- Only `APP_ENV=production` is indexable. All other environments emit noindex/nofollow metadata and a site-wide robots disallow rule.
- The existing Render services are configured in place. Do not create a duplicate Blueprint or a second production database.
- Render web service and PostgreSQL stay in Frankfurt so the internal database URL is usable and latency remains predictable for the selected deployment.
- Provider credentials are entered directly in Render, Cloudflare, SMTP, Turnstile, and Sentry dashboards. They never enter chat, git, screenshots, or documentation.

- [ ] **Step 3: Add shared escaping helpers**

Create:

```ts
const HTML_ENTITIES: Record<string, string> = {
  "&": "&amp;",
  "<": "&lt;",
  ">": "&gt;",
  '"': "&quot;",
  "'": "&#39;",
};

export function escapeHtml(value: unknown) {
  return String(value ?? "").replace(/[&<>"']/g, (character) => HTML_ENTITIES[character]);
}

export function sanitizeEmailHeader(value: unknown) {
  return String(value ?? "").replace(/[\r\n]+/g, " ").trim().slice(0, 200);
}
```
